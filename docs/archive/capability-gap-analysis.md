# FirmHound 能力差距自查（2026-09 版）

> **已归档**：2026-09 的一次系统性能力自查。当时对照一份外部能力基线与系统代码现状逐条核对，结论按当时状态记录，仅作决策留痕；环境、路径、开关可能与当前实现不一致。

> 2026-08-30 首版，2026-09-01 按仓库与 CI 复核更新。下面按项列出，每条可单独核对。

---

## 一、评估标准

按五个能力维度自查（这套维度是评审一套智能体系统时的通用切面，也适合作为自研系统的检查表）：

| 维度 | 关注点 |
|---|---|
| 任务理解与执行设计 | 能否把自然语言任务/输入材料转成可执行的阶段计划，并在失败时重规划 |
| 系统架构与工程实现 | 模块化、契约化、可部署、可测试、依赖是否可控 |
| 决策逻辑与可解释性 | 结论是否有证据与反证支撑，链路是否可追溯 |
| 工具协同与扩展能力 | 外部工具如何接入、如何融合、缺失时如何降级 |
| 能力边界与演进 | 当前覆盖范围是否写清楚，后续扩展成本如何 |

## 三、仍是缺口的部分

**结论：当前系统是固件漏洞挖掘流水线，尚不能跨场景复用。** 它覆盖"漏洞挖掘 → 固件"这一窄子集，不具备开放式任务自主规划与跨工具闭环决策。这个边界是合理的产品选择，但要在文档里写清楚。

| 能力维度 | 现状 | 差距 |
|---|---|---|
| 任务理解与执行设计 | 部分具备 | 有自然语言槽位提取、压缩包入口与 quick/standard/full 计划，但仍是启发式阶段模板，不能跨场景重规划 |
| 系统架构与工程实现 | 基本具备 | ToolRegistry / 阶段机 / Schema 契约是真实资产；缺一键部署、缺容器镜像，依赖较重的外部工具链 |
| 决策逻辑与可解释性 | 基本具备 | 有 DecisionStore / EvidenceStore / 10 问反证 / 外部交叉验证；缺面向人的交互式证据链可视化 |
| 工具协同与扩展能力 | 基本具备 | 双轨汇聚 + 四个外部分析器 + Skill 化；但外部工具**真实运行**未验证，"协同"缺实测背书 |
| 能力边界与演进 | 缺失 | 边界未在文档中统一声明；多场景（渗透/应急/逆向）能力为零，架构完全面向固件 |

**系统目前完全没有的：**

1. **真实工具运行证据**：四个外部工具的真实跑（Ghidra/KLEE/仿真器/容器）从未在本机跑通，全部被环境阻断；fixture 结果不能表述成真实复现。
2. **一键部署形态**：没有 Dockerfile / compose / 一键脚本，依赖项靠手工装，受控环境能否跑起来是风险。
3. **可对外访问的入口**：只有本地 CLI，没有对外服务（如需在线演示或远程交付）。
4. **受控环境适配**：当前假设宿主机有 Ghidra/KLEE/QEMU 与足够资源（Ghidra 需 ≥16G 内存）。
5. **文档定稿**：开发计划、Skill、外部分析器说明、部署与挖洞教程已具备；正式设计文档、测试报告、用户手册、技术报告仍需按纲目定稿。

## 四、需要外部条件才能推进的事项

下面这些不属于代码缺口，需要真实账号、真实环境或领域判断：

1. **真机执行**：四个外部工具的真实运行 + Tenda AC15 固件下载。脚本已就绪，但需要一台有公网 egress、资源足够（Ghidra ≥16G 内存、Docker 或 KLEE 工具链）的机器。跑出来的数据是能力证据的唯一来源。
2. **模型接入**：如需 LLM 增强，要提供可配置的网关适配层与合规的模型账号；账号与审批不在代码范围内。
3. **受控环境部署验证**：需要一台干净的目标机器/镜像做端到端验证，本地开发生态无法替代。
4. **边界定位**：继续扩场景（渗透/应急/逆向）是架构级改造，工作量以周计；或者明确收敛为"固件漏洞挖掘垂直能力 + 双轨汇聚"。**定位不同，后续工作也不同，需要负责人拍板。**
5. **领域知识与演示素材**：真实案例的选择、为什么这套设计能提升效率——需要安全领域判断，代码本身给不出。

---

## 五、可继续推进的代码/文档项

- **NL 任务入口 + 任务驱动规划器**：自然语言/接口文档/压缩包 → 解析 → 动态生成执行计划（当前最大的可补代码缺口）。
- **部署包**：Dockerfile + compose + 一键脚本，固定工具链版本，去掉对宿主环境的隐式假设。
- **推理链可视化**：把 DecisionStore/EvidenceStore 渲染成"决策依据链"视图。
- **文档全套定稿**：设计 / 开发 / 测试 / 用户手册 / 技术报告（见 `docs/design/`）。
- **真机 runbook**：四工具真实运行的分步命令与验收判据。
- **模型网关适配层**：前提是拿到账号与接入规范。

---

## 六、结论

- **工程主链**：代码、契约、回写、报告与 CI 已齐，**缺的是真实工具与真实固件的复现证据**。不能把 fixture 结果表述成真实复现。
- **交付形态**：仍有三个硬缺口——① 可复现的部署包；② 受控环境验证；③ 文档定稿。优先级：真机跑四工具拿数据 → 定边界 → 部署包 → 文档定稿。
- **需要人来做**：第四节 5 项（真机执行、模型账号、受控环境验证、边界决策、领域判断）无法由代码替代。
